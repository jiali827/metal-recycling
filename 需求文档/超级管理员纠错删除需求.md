### 本次修订摘要（V1.1）

- 将“业务状态”和“数据状态”拆分，合同、过磅台账、结算单、收付款列表统一展示两列状态。
- 明确过磅台账的“作废”属于数据状态，不再作为唯一页面的特殊状态。
- 明确操作入口分层：草稿/待确认使用普通删除，已确认且正常使用纠错删除，已作废/已撤销/已冲正只查看。
- 新增超级管理员独立“永久清理”入口要求；普通业务列表不提供物理删除已确认事实的垃圾桶入口。
- 结算单已确认记录的纠错与合同、过磅台账、收付款统一使用同一个影响预览弹窗，不因存在收付款而跳转收付款页面处理。

### 本次修订摘要（V1.2）

- 明确纠错批次号的格式、生成时机、租户范围、流水规则、并发唯一性和幂等要求。

## 1. 背景与目标

合同、过磅台账、结算单和收付款具有严格的前后置关系。确认后的数据可能仍然录入错误，但直接物理删除会破坏合同履约、应收应付、核销和现金口径，也会使历史无法追溯。

本需求新增租户内超级管理员的“纠错删除”和“永久清理”能力：普通用户界面必须区分普通删除、纠错删除和查看；系统内部必须通过撤销、作废、冲销和审计完成可追溯的逆向处理。除无副作用草稿外，默认不允许物理删除业务事实；已作废、已撤销、已冲正记录只能查看，永久删除必须从独立的超级管理员清理入口执行。

## 2. 范围与术语

### 2.1 适用范围

- 适用于单个租户内部的超级管理员。
- 处理对象包括：采购合同、销售合同、过磅台账、结算单、应收/应付、收付款及收付款核销分配。
- 超级管理员可以突破普通角色的操作权限，但不能突破数据一致性、职责记录和审计要求。
- 跨租户平台运营删除、数据库级数据清理、法定保留期后的归档清理不在本期范围内。

### 2.2 术语定义

| 术语 | 适用对象 | 含义 |
|------|----------|------|
| 物理删除 | 未确认且无引用的草稿 | 从业务数据表移除；仍需保留操作审计 |
| 撤销 | 合同确认、结算单确认、确认动作 | 取消此前的业务确认决定，原记录保留 |
| 作废 | 过磅台账、应收/应付等业务单据 | 单据不再产生业务效力，编号和历史保留 |
| 冲销 | 收付款、核销分配、账务金额 | 通过反向记录或反向分配抵消原账务影响 |
| 关闭 | 合同等业务对象 | 业务正常结束，不表示纠错或删除 |

### 2.3 双状态模型

合同、过磅台账、结算单和收付款必须分别维护并展示两个维度的状态，禁止使用一个 `status` 字段同时表达业务流程和数据是否仍有效。

| 状态维度 | 适用对象 | 示例值 | 用途 |
|----------|----------|--------|------|
| 业务状态 | 合同 | 草稿、生效、履约中、已完成、已关闭 | 表示业务生命周期和是否可以进入下一环节 |
| 业务状态 | 过磅台账 | 待确认、已确认 | 表示是否完成过磅确认 |
| 业务状态 | 结算单 | 待确认、已确认 | 表示是否完成结算确认 |
| 业务状态 | 收付款 | 待确认、已确认 | 表示是否完成正式入账 |
| 数据状态 | 四类业务对象 | 正常、作废、已撤销、已冲正 | 表示记录是否仍产生业务效力以及是否经过纠错处理 |

列表必须同时提供“业务状态”和“数据状态”列；如某对象没有对应业务状态，显示“—”，不得省略数据状态列。状态筛选也必须按两个维度分别提供。

界面不得将所有状态都显示为“已删除”。详情页需要同时展示用户可理解的“纠错删除”结果和具体业务状态，例如“已作废（超级管理员纠错）”。

## 3. 删除策略总览

| 对象及状态 | 是否允许物理删除 | 超级管理员处理方式 |
|------------|------------------|--------------------|
| 草稿，且无下游引用 | 允许 | 物理删除；记录操作者、时间和原因 |
| 已确认，且无下游引用 | 不允许 | 标记为已撤销，保留原单据 |
| 已确认，存在下游引用 | 不允许 | 展示影响链路，按依赖逆序执行纠错 |
| 已产生收付款或核销 | 不允许 | 先冲销指定核销分配；实际现金变化需另登记退款/反向收付款 |
| 已撤销/已作废/已冲销 | 普通业务页面不允许删除 | 仅查看；如需彻底移除，进入独立的超级管理员永久清理流程 |

### 3.1 统一原则

1. 业务事实默认只追加状态和反向流水，不覆盖或删除原记录。
2. 纠错必须按“先下游、后上游”的逆向顺序执行。
3. 所有影响计算和写入由后端完成，前端不得自行级联修改多张业务表。
4. 一次纠错生成唯一 `reversalBatchId`，所有相关撤销、作废、冲销和审计事件使用同一批次号。
5. 默认报表、余额、履约和可关联列表排除已撤销/已作废/已冲销影响；审计和追溯页面仍可查看完整历史。
6. 已确认、正常数据不显示普通删除图标；已作废、已撤销、已冲正数据不显示删除或纠错图标，只显示查看图标。

### 3.2 纠错批次号规则

纠错批次号是一次跨对象纠错操作的业务追踪编号。它必须由服务端在纠错执行时生成，前端预览阶段不得提前生成或占用批次号。

#### 编号格式

```text
RB-YYYYMMDD-NNNN
```

示例：

```text
RB-20260825-0001
```

字段规则如下：

| 部分 | 规则 |
|------|------|
| `RB` | 固定前缀，表示 Reversal Batch（纠错批次） |
| `YYYYMMDD` | 纠错执行日期，使用当前租户配置的业务时区和服务端时间；不使用客户端时间，也不取被纠错单据日期 |
| `NNNN` | 当日四位流水号，范围 `0001`–`9999` |

#### 生成与唯一性

1. 流水号按“租户 + 执行日期”独立递增；每个租户每天从 `0001` 开始。
2. 同一租户、同一执行日期的批次号不得重复，数据库必须建立唯一约束。
3. 批次号一经生成即不可修改、不可复用。因事务失败产生的流水号空洞可以保留，不允许用后续批次填补。
4. 当日流水号达到 `9999` 时，系统必须阻止继续执行并提示管理员联系系统维护人员扩容规则，不得生成五位流水号或截断编号。
5. 批次号生成必须在服务端事务中完成，采用数据库原子递增或等价的并发安全机制；禁止使用前端时间戳、随机数或列表数量推算。
6. 同一次纠错影响的所有对象、反向流水和审计事件必须保存完全相同的 `reversalBatchId`。
7. 重复提交同一幂等请求时，系统返回第一次执行生成的批次号和处理结果，不得再次生成新批次或重复执行反向处理。
8. 批次号只用于业务追踪展示和关联查询；如系统需要技术主键，可另设不可展示的 UUID/ULID，不得用技术主键替代批次号规则。

#### 展示与查询

- 纠错成功反馈、业务详情、审计记录和批次查询页面统一展示完整批次号，例如 `RB-20260825-0001`。
- 列表不强制增加批次号列，但必须支持在详情或审计入口查看并复制批次号。
- 批次号查询必须限定当前租户；普通用户只能查看其权限范围内的批次，超级管理员可查看当前租户全量批次。

## 4. 依赖链与逆向处理

### 4.1 业务依赖

```text
合同确认
  -> 过磅台账确认
  -> 结算单确认
  -> 应收/应付
  -> 收付款及核销分配
```

### 4.2 合同纠错删除

当超级管理员删除合同，系统必须先计算并展示所有直接或间接关联数据。确认后按以下顺序处理：

1. **收付款**：仅冲销本合同关联往来的指定核销分配；原收付款记录保留。若实际资金已发生，不自动假设退款完成。
2. **结算单**：撤销结算单确认状态；保留结算单、明细、确认人和确认时间。
3. **过磅台账**：将关联正常磅单作废；保留 BX 单号，不能释放或复用；回滚合同履约量。
4. **应收/应付**：将由关联磅单生成的往来标记为已作废，不再参与余额和核销。
5. **合同**：最后将合同标记为已撤销，记录原因、操作者、时间和纠错批次号。

系统不得在合同仍有正常磅单、有效结算单或未处理核销时只删除合同主记录。

### 4.3 过磅台账纠错删除

1. 若存在本磅单对应的未冲销核销分配，先返回阻断信息并要求先冲销；超级管理员强制纠错也必须生成冲销记录，不能静默跳过。
2. 将磅单标记为已作废，BX 单号永久占用。
3. 将对应且仅对应的一笔应收/应付标记为已作废。
4. 回滚合同履约量；若回滚后无正常磅单，合同履约中状态恢复为可选用状态；已完成合同是否允许重开按现有规则执行，默认不自动重开。

### 4.4 结算单纠错删除

1. 点击结算单纠错入口后，直接打开统一纠错影响预览弹窗；不得先弹出“去收付款”阻断提示。
2. 若结算单已经产生应收/应付或存在收付款核销，在同一弹窗中列出收付款、核销分配和应收/应付影响，并在提交时按依赖逆序自动处理。
3. 将结算单标记为已撤销，原确认信息保留。
4. 与结算单直接关联的往来标记为已作废或恢复为未确认前状态，具体由后端根据现有数据来源判断；不得产生孤立可核销往来。
5. 结算单纠错不反向作废来源磅单；来源磅单是否纠错应由用户单独从过磅台账发起纠错流程。
6. 因系统没有独立的应收/应付业务页面，影响预览不单独展示“作废往来”明细行；该动作作为结算单纠错的内部联动执行，并在提示语和账务影响数量中体现。

### 4.5 收付款纠错删除

1. 不物理删除原收付款。
2. 按指定 `allocationId` 冲销核销分配；一笔收付款核销多个往来时，只处理选中的分配行。
3. 已冲销分配生成反向账务记录或等价的不可篡改冲销流水，使对应往来的 `settledAmount`、`balance` 和 `status` 回退。
4. 若需要退回实际现金，另登记退款/反向收付款；“冲销核销”本身不代表现金已退回。
5. 收付款状态显示为“部分冲销”或“已冲销”，不得显示为普通“已删除”。

## 5. 纠错删除交互

### 5.1 入口

- 合同、过磅、结算单和收付款详情/列表提供“纠错删除”入口。
- 仅具备对应权限且记录为已确认、正常状态时展示“纠错删除”入口；已作废、已撤销、已冲正记录不展示该入口。
- 草稿/待确认且无下游引用的数据展示普通删除入口；普通删除使用垃圾桶图标并执行二次确认。
- 已确认、正常数据不展示垃圾桶图标，使用独立的纠错图标（例如反向箭头），图标标题必须明确为“纠错删除”。
- 已作废、已撤销、已冲正数据只展示眼睛查看图标，不展示删除、纠错或编辑图标。
- 普通删除入口不得直接删除已确认业务事实。

### 5.2 超级管理员永久清理入口

永久清理不是普通删除，也不是纠错删除，必须在独立的“系统管理 / 数据清理”入口中提供，仅超级管理员可见。

- 清理对象：已作废、已撤销、已冲正且不存在有效业务引用的历史记录。
- 清理入口：独立菜单或审计/历史记录页中的“永久清理”操作，不复用列表垃圾桶图标。
- 清理前置：系统重新执行关联检查；存在有效关联、未完成纠错链、未完成审计写入或仍参与有效余额时禁止清理。
- 清理确认：展示原始单号、对象类型、数据状态、关联数量和不可恢复警告；必须填写清理原因，并输入当前单号或确认短语后提交。
- 清理结果：物理移除业务记录，但保留不可修改的清理审计记录，包括原记录 ID、摘要快照、原状态、清理人、清理时间、原因和清理批次号。
- 幂等规则：已清理对象再次访问时显示“记录已永久清理”及审计批次，不允许重复执行。
- 当前原型状态：尚未提供独立的永久清理页面；本节为本次需求必须补充的设计和实现范围。

### 5.3 影响预览弹窗

点击入口后，系统先读取后端影响分析结果，展示：

| 区块 | 必须展示内容 |
|------|--------------|
| 当前对象 | 单据类型、单号、客户、日期、当前状态、金额/重量摘要 |
| 直接关联 | 关联合同、磅单、结算单、应收/应付、收付款和核销分配数量 |
| 预计动作 | 每条关联数据将执行撤销、作废、冲销或保留 |
| 业务影响 | 履约量回滚值、余额回退值、现金口径变化、BX 占号保留说明 |
| 阻断项 | 无法自动处理的核销、已完成合同、并发版本冲突等 |

预览接口只读，不产生数据变更。若影响分析失败，不展示确认提交按钮。

### 5.4 二次确认与原因

- 管理员必须勾选“我已确认上述影响范围”。
- 必须填写纠错原因，去除首尾空格后至少 1 个字符即可提交，不设最小字数限制；建议最长不超过 500 个字符，禁止仅输入空格。
- 对高风险操作再次要求输入当前单号或确认短语，具体以页面交互为准。
- 提交按钮在请求期间禁用，防止重复提交。

### 5.5 成功反馈

成功后展示：纠错批次号、处理对象数量、各对象最终状态和审计入口。

失败时保留当前页面和原因输入，展示明确错误码/错误文案，并允许重新获取影响预览后重试。

## 6. 权限规划

权限按能力拆分，不把超级管理员能力混入普通 `delete`：

| 权限点 | 操作范围 | 数据范围 |
|--------|----------|----------|
| `delete_draft` | 删除未确认且无引用草稿 | 当前租户全量草稿 |
| `void_confirmed` | 撤销已确认对象、作废已确认单据 | 当前租户全量业务数据 |
| `reverse_allocation` | 冲销指定收付款核销分配 | 当前租户全量收付款和往来 |
| `force_reverse_chain` | 预览并执行跨对象逆向纠错 | 当前租户全量业务数据 |
| `purge_voided` | 永久清理已作废、已撤销、已冲正且无有效引用的数据 | 当前租户全量历史数据 |
| `view_audit` | 查看纠错批次、原记录、反向流水和操作日志 | 当前租户全量审计数据 |
| `restore_voided` | 恢复可安全恢复的撤销/作废对象 | 当前租户全量相关数据 |

本期不提供跨租户删除权限。服务端每次请求必须同时校验用户权限、租户上下文、对象状态和版本号。

## 7. 数据与接口要求

### 7.1 业务字段

确认型对象至少增加或统一支持：

| 字段 | 说明 |
|------|------|
| `status` | 正常、已撤销、已作废、部分冲销、已冲销等业务状态 |
| `businessStatus` | 草稿、待确认、生效、已确认、已完成、已关闭等流程状态；按对象支持的枚举实现 |
| `dataStatus` | 正常、作废、已撤销、已冲正；所有四类业务对象统一支持 |
| `confirmedAt` / `confirmedBy` | 原确认时间和确认人 |
| `voidedAt` / `voidedBy` | 作废/撤销时间和操作者 |
| `voidReason` | 纠错原因 |
| `reversalBatchId` | 关联纠错批次号，格式为 `RB-YYYYMMDD-NNNN`；由服务端生成且不可修改 |
| `version` | 乐观锁版本，关键写入必填 |

收付款核销分配必须具备独立 `allocationId`，支持按分配行冲销；冲销流水必须可关联原分配和原收付款。

### 7.2 接口建议

| 接口 | 说明 |
|------|------|
| `POST /correction-impact-preview` | 生成只读影响预览，不写数据 |
| `POST /contracts/{id}/force-reverse` | 按事务执行合同逆向纠错 |
| `POST /weigh-tickets/{id}/void` | 作废磅单，执行往来和履约联动 |
| `POST /settlement-docs/{id}/void-confirmation` | 撤销结算单确认 |
| `POST /payments/{id}/reverse` | 按分配行冲销核销 |
| `GET /reversal-batches/{id}` | 查看纠错批次及处理结果 |
| `GET /audit-events` | 查询不可篡改审计事件 |
| `POST /purge-records/preview` | 预览永久清理对象及有效引用检查，不写数据 |
| `POST /purge-records/execute` | 超级管理员执行永久清理并写入清理审计记录 |

接口命名可按后端资源规范调整，但必须保持“预览”和“执行”分离。

### 7.3 事务与幂等

- 影响分析与执行之间必须校验对象 `version`；版本变化则拒绝执行并要求重新预览。
- 跨对象纠错必须在一个数据库事务中完成；任一步失败则整体回滚。
- 请求必须支持幂等键；重复提交不得重复冲销、重复回滚履约量或生成重复反向流水。
- 失败响应应至少区分：`PERMISSION_DENIED`、`VERSION_CONFLICT`、`SETTLEMENT_BLOCKED`、`ALREADY_REVERSED`、`INVALID_REASON`、`TRANSACTION_FAILED`。

## 8. 审计与查询口径

审计事件至少记录：租户、操作者、操作类型、对象类型与 ID、原状态、目标状态、原因、纠错批次号、请求时间、版本、关联对象和结果。

审计记录不可由业务页面删除或编辑。业务列表和报表默认排除已撤销/已作废/已冲销影响，但支持按状态筛选历史记录。项目全景、单据详情和审计页面可查看完整纠错链路。

### 8.1 列表状态与操作矩阵

四个业务列表必须按以下矩阵展示状态列和操作图标，避免用户把物理删除、纠错处理和查看混淆。

| 对象 | 业务状态列 | 数据状态列 | 编辑图标 | 普通删除图标 | 纠错图标 | 查看图标 |
|------|------------|------------|----------|--------------|----------|----------|
| 合同 | 草稿/生效/履约中/已完成/已关闭 | 正常/已撤销/作废 | 仅草稿 | 仅草稿 | 已确认且正常 | 已锁定或已作废 |
| 过磅台账 | 待确认/已确认 | 正常/作废 | 仅待确认 | 仅待确认 | 已确认且正常 | 已作废 |
| 结算单 | 待确认/已确认 | 正常/已撤销/作废 | 仅待确认 | 仅待确认 | 已确认且正常 | 已确认、已作废 |
| 收付款 | 待确认/已确认 | 正常/已冲正 | 仅待确认 | 仅待确认 | 已确认且正常 | 已冲正 |

已确认记录不得显示垃圾桶图标；已作废、已撤销、已冲正记录不得显示编辑、普通删除或纠错图标。永久清理只从独立的超级管理员清理入口进入。

## 9. 状态与异常场景

| 场景 | 页面表现 | 处理规则 |
|------|----------|----------|
| 无影响关联 | 预览显示仅处理当前对象 | 符合条件后允许提交 |
| 存在未冲销核销 | 明确列出阻断对象 | 必须先冲销指定分配，或由强制纠错流程自动生成可追溯冲销 |
| 已完成合同 | 显示履约回滚风险 | 默认拒绝自动重开；需要单独特批规则 |
| 并发修改 | 提示数据已变化 | 重新获取预览，不得覆盖他人修改 |
| 重复点击/重复请求 | 返回原纠错批次 | 不重复产生反向记录 |
| 权限不足 | 隐藏入口或返回无权限 | 不泄露跨权限对象明细 |
| 后端事务失败 | 显示失败原因和批次状态 | 整体回滚，允许重新预览和重试 |
| 实际现金未退回 | 明确提示“仅冲销核销，不代表退款” | 通过独立退款/反向收付款流程处理 |

## 10. 验收标准

| 验收点 | 验收标准 |
|--------|----------|
| 草稿物理删除 | 未确认且无引用草稿可删除；有引用时拒绝物理删除 |
| 合同纠错 | 删除合同前展示完整影响链；确认后按收付款、结算、磅单、往来、合同逆序处理 |
| 过磅作废 | 作废后 BX 单号保留，对应往来失效，合同履约量正确回滚 |
| 结算撤销 | 已确认结算单不能直接删除；撤销后原确认信息和关联链路仍可追溯 |
| 核销冲销 | 多往来收付款只冲销指定分配行；往来余额和状态正确回退 |
| 现金语义 | 冲销核销不被错误展示为现金退款；实际退款需要独立业务记录 |
| 权限隔离 | 只有具备对应纠错权限的当前租户用户可执行；不能跨租户操作 |
| 原因与审计 | 每次纠错必须填写原因，并生成包含前后状态和批次号的审计记录 |
| 原子性 | 跨对象纠错任一步失败时全部回滚，不产生半完成链路 |
| 幂等性 | 重复提交不重复生成冲销流水或履约回滚 |
| 默认口径 | 已撤销、已作废、已冲销数据不参与默认余额、履约和经营统计 |
| 历史追溯 | 单据详情、项目全景和审计页可查看原单、纠错原因、关联反向记录 |
| 双状态展示 | 合同、过磅、结算单、收付款列表均同时展示业务状态和数据状态；作废、撤销、冲正状态可直接筛选 |
| 操作图标区分 | 草稿/待确认显示普通删除；已确认正常显示纠错图标；已作废/已撤销/已冲正只显示查看图标 |
| 永久清理入口 | 普通业务列表不提供永久删除；超级管理员可从独立清理入口预览并清理符合条件的历史记录，且生成清理审计 |

## 11. 范围边界

### 11.1 本期包含

- 租户内超级管理员纠错删除入口。
- 影响预览、原因填写、二次确认和结果反馈。
- 草稿物理删除与确认数据的撤销/作废/冲销区分。
- 四类业务列表的业务状态/数据状态双列展示，以及普通删除、纠错删除、查看图标区分。
- 超级管理员独立永久清理入口、有效引用检查和清理审计记录。
- 合同、过磅、结算、往来、收付款的逆向处理规则。
- 按核销分配行冲销、事务、幂等、乐观锁和审计要求。
- 状态、列表和统计口径调整。

### 11.2 本期不包含

- 跨租户平台运营删除。
- 未通过永久清理流程的数据库直接删除、批量无条件清库。
- 自动办理银行退款、现金退回或第三方支付退款。
- 已完成合同自动重开；如需要，另立特批状态机需求。
- 法务归档、保留期清理和完整会计凭证总账。

## 12. 给实施 AI 的执行约束

1. 先读取现有实体类型、MockStore、业务规则总表和相关测试，再修改代码。
2. 不把超级管理员权限实现为绕过所有业务规则的万能删除；必须遵守本 PRD 的逆向处理和审计要求。
3. 优先抽取纯业务函数：影响分析、状态转换、核销分配冲销、履约回滚和幂等判断；再接入页面和 Store/API。
4. 为每种对象至少补充“无引用草稿删除、已确认纠错、存在核销阻断、重复执行、事务失败”测试。
5. 修改页面、实体、Mock 数据和接口文档时，保持业务状态与数据状态分离，不将“撤销”“作废”“冲销”混用。
6. 普通业务列表不得通过垃圾桶图标触发已确认数据处理；纠错图标、查看图标和永久清理入口必须有独立语义和权限校验。
